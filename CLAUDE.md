# TPN: rules for the assistant

**The repository is TPN, the game is Sparkle Valley (owner, 24 Oct 2026 AEDT).** The repository is called `tpn` and its front notes (README, these headings) say TPN, so the project stays low-key on GitHub. The game inside it is **Sparkle Valley · Thung Lũng Lấp Lánh**: build it, name it and show it to players under that name everywhere (title screen, website, voices, Studio, store text). Only the front notes say TPN; the other docs keep "Sparkle Valley".

**Version numbers (owner, 24 Oct 2026 AEDT):** v, the major number, a point and two digits, everywhere (inside and on screen): r90 was the public launch shown as v1, then v1.01, v1.02 ... v1.99; a big upgrade starts v2.00. No more "r" numbers for new builds; old ones are still read (`netlify/lib/build-number.mts`). Only Release sets the number, and never without the owner.

**Where the notes live:** [docs/README.md](docs/README.md) lists where the rules, requirements, design, board and plans are; finished round reports are in `docs/history/` (owner, 24 Oct 2026 AEDT: tidied, nothing deleted).

**Website consistency and layout (owner, 23 Oct 2026 AEDT):** read [the website/game contract](docs/website-review-20261023/WEBSITE-RULES.md) and [Release integration handoff](docs/website-review-20261023/RELEASE-HANDOFF.md) before changing website content, UI or packaging. Keep full bilingual detail and four main destinations; use the same game source/art/fonts/theme/release and review drift. Website belongs on Welcome and in Settings during play; removing HUD Home must also reclaim safe quest-bar space. Those runtime changes are pending Release, not already made by the website branch.

**Owner-approved UI and future-feature rules (14 Oct 2026 AEDT):** read the section “Owner-approved interface and feature rules” in [the design handbook](docs/SO-TAY-THIET-KE.md) (UX-001–UX-010) before planning or changing a feature. Work order and implementation sequence: [owner UI audit](docs/cores/tasks/owner-ui-audit-20261014.md). Approval to write these rules does not deploy runtime changes.


**HARD RULE: nothing reaches `main` (and so Netlify) until the owner has checked the round and clearly said "yes, deploy".**
- Commit locally as you go.
- When a round is done, show what changed and how it was tested, and give the Netlify zip. No local bundle (owner, 11 Oct: the offline files are on GitHub and Google Drive; the Netlify zip is still wanted).
- History: 4 Oct standing "push without asking" ended 5 Oct ("ask me every time"); 5 Oct "ask GitHub and Netlify separately" replaced 10 Oct by the rule below.
- **Artifacts always go into the repo (owner, 10 Oct: "Always allow adding artifact to repo").** Whenever a design, plan or drawing page is made or updated as a claude.ai artifact, put a copy in the repo (the page and its pictures, under `docs/<name>/`) and link it from the docs that use it, so every chat can read it. This is allowed without asking, and the push of such a docs-only commit to the working branch needs no separate "yes, push". Merging into `main` still needs "yes, deploy", and anything that changes the game still needs "yes, push".
- The Google Drive mirror and the voice relay (TURN) are set up (owner, 10 Oct AEST): no more reminders.

**Release is the master release of all work (owner, 10 Oct):**
- Helper chats (every core that is not Release) push to their own branch (`core/<name>` or the branch their session was given) whenever their checks pass, without asking the owner. Never to `main`.
- Release collects every branch, merges them, runs the full suite, reports the round (what changed, how tested, the Netlify zip), then asks the owner **one pop-up question per round: "yes, deploy"**. That one answer covers pushing the release branch and merging it into `main` (Netlify publishes). Nothing reaches `main` without it, and it covers that round only.
- **The bug robot (owner, 10 Oct)** works like a helper chat: the GitHub workflow `.github/workflows/bug-fixer.yml` starts the moment a bug is filed, labelled or gets the owner's "go", with a 5-minute timer as a backup (owner, 10 Oct), picks up open GitHub issues labelled `bug` plus a core label (Analytics & Infra files them, following `docs/cores/front-desk.md`), and lets Claude work on them as that core. A **small** bug (the small-bug rule in `docs/cores/front-desk.md`) is fixed, checked and pushed without asking, only to its own branch `bugfix/<core>-<issue>` with a draft pull request; a **big** bug gets a plan on the issue and waits for the owner's "go". It never pushes to `main`: Release merges its pull requests in a round, under that round's "yes, deploy".

**Checks and the full suite (owner, 13 Oct AEDT):** run them with `tests/suite.mjs`, not `run.mjs` alone. (1) **A change** (a film, a button fix, a helper chat's work, a film batch): `cd tests && node suite.mjs --changed` runs only the checks for what changed since main (the quick checks without a browser, `boot`, `phone`, `contract`, and the checks that run the changed code, from `tests/check-map.json`); a file it cannot place sends it to the full suite. `--list` shows the choice without running. **If `--changed` picks the full suite** (it says "Full suite: ...", for example after a change to a shared file or to test code), do not run it locally: push the branch and start `.github/workflows/full-suite.yml` by hand on it (owner, 17 Oct AEDT). (2) **A release, before every "yes, deploy" (owner, 14 Oct AEDT, after r71 compared both):** the full suite runs **on GitHub** (`.github/workflows/full-suite.yml`: 8 machines side by side, about 30 minutes, its summary posted on the release pull request; it starts with the pull request and with each push to it). Locally Release runs only the speed checks, each alone: `cd tests && node suite.mjs --jobs 1 --only perf,battery,startup` (GitHub's shared machines measure speed badly), plus the phone, tablet and computer screenshots. A check that is red on GitHub is fixed, not waved through; one that passed only on its second try is named in the report. The local full suite (`node suite.mjs`, about 2.5 to 3 hours here) is only for when GitHub's is down. The code map: commit the `check-map` artifact's `tests/check-map.json` and `tests/check-times.json` from the GitHub run. (3) **The slowest checks** (`reading`, `films`, `voicearea`) test a sample that changes every run (their result says SAMPLE) and everything when their own files changed since main; `node suite.mjs --all` forces everything. Never run two suites or test runs at once beside `suite.mjs` (it already uses the machine). The result is in `tests/out/suite-result.txt`.

**Phone, tablet and computer (owner, 8 Oct):** every change is checked on a phone, a tablet and a computer so it looks tidy on all three (rule UI-006, check `phone`); look at screenshots of all three before reporting a round.

**Questions to the owner (owner, 10 Oct): always ask with pop-up questions** (the question tool with clickable choices), never as questions in plain text. This covers every question: the plan's "go", choices between options, unclear answers, and "yes, deploy". Give each question 2 to 4 short choices, the recommended one first and marked "(Recommended)"; the owner can always type their own answer instead. Applies to every chat (Release and every core).

**No answer within 15 minutes: carry on (owner, 17 Oct AEDT).** A chat never sits idle waiting for the owner.
1. **Work that does not need the answer goes on** while a question is open: other items of the brief, checks, pictures, docs.
2. **After 15 minutes without an answer** (Sydney time from when the question was asked), the chat carries on with the choice it marked "(Recommended)". It writes the choice as "assumed, owner can change" on its board line and in its core file under "Owner's decisions", and names it in its next report. If the owner later answers differently, the chat changes the work to the owner's answer.
3. **Never assumed, always wait for the owner:** "yes, deploy" (merging into `main`, Netlify), the version number, deleting or overwriting children's saves or family data, keys, payments and anything else that cannot be undone. While one of these waits, the chat carries on with everything else.
4. **Ready for Release while waiting:** a finished part goes to the board as "ready for Release" with its assumed choices listed, so Release can collect it; the round's single "yes, deploy" still decides whether it ships.
5. The question tool holds the chat until it is answered, so a chat that knows it will need a decision later asks it as early as possible, and for a choice that would stop the work it makes the recommended choice first (as in step 2) and asks for confirmation at its next report.

**Times and dates:** always give them in Sydney time (Australia/Sydney): AEDT (UTC+11) during daylight saving, from the first Sunday in October to the first Sunday in April, and AEST (UTC+10) the rest of the year, labelled AEDT or AEST as it applies, in messages, reports and documents (owner, 10 Oct; was Brisbane time). Convert from UTC (GitHub, Netlify, logs) before quoting.

**Cores (owner, 8 Oct):** the project is split into 8 cores, one AI chat per core (World, Play, Kid UI, Voice & Audio, Online, Studio, Analytics & Infra, Release). If the owner says which core you are, read `docs/cores/README.md` and your core's file in `docs/cores/` before anything else, work only in that core's files on the branch `core/<name>`, and put requests for other cores on `docs/cores/BOARD.md`. Only the Release core merges, runs the full suite, reports, collects every branch and asks for "yes, deploy". With no core named, you are Release.

**Bug intake (owner, 11 Oct, 7:40 pm AEDT):** the Front Desk is no longer a separate service. Analytics & Infra receives bugs and questions, finds the owning core and files issues for the bug robot, using the intake and small/big rules in `docs/cores/front-desk.md`. Release still owns integration and the round's explicit "yes, deploy". This supersedes the 10 Oct Front Desk-only rule.

**Working together across chats and Claude accounts (owner, 10 Oct).** Chats, even on different Claude accounts, cannot see or message each other; the GitHub repo is their only shared memory, and the owner carries messages between them.
1. **Start of every session:** `git fetch` and `git pull` your branch, merge `main` into it, then read `docs/cores/BOARD.md` (the whole board, not only your section) and your progress notes.
2. **The board is the status page.** Keep your core's "Now" line on `docs/cores/BOARD.md` current: what you are doing, your branch, your last commit, and what you are waiting for. When your work is finished and pushed, write **"ready for Release"** in it: Release checks every branch once an hour and merges the ones marked ready (owner, 10 Oct). Requests to another core go there in the board's format. Update it before every report.
3. **Pull before every push** (`git pull --no-rebase` on your branch, fix any conflict, run the checks again if code changed). Never force-push.
4. **Decisions the owner makes in your chat go into your core file** under "Owner's decisions" in the same session, so other chats and Release know them.
5. **Designs and pages from claude.ai go into the repo** (`docs/<name>/`), because chats on other accounts cannot open another account's artifacts.
6. **Keys live in each account's environment settings**, never in the repo. A chat without `AZURE_SPEECH_KEY` lists new spoken lines on the board for Release to record.
7. **Only Release merges into `main` and deploys.** Release reads the board, every branch on GitHub and each progress note before merging, and gives the owner a status summary when asked "what's the status?".

**Helper chats (owner, 10 Oct): every chat that is told it is a core (not Release) keeps these rules, whether or not the owner pastes them.**
1. Read this file, `HANDOFF.md`, `docs/cores/README.md`, your core's file in `docs/cores/` and, if the owner names one, your task brief in `docs/cores/tasks/`. The brief says what to build; this file and the docs say how. If they disagree, the docs win: say so.
2. **Plan first and wait:** before changing anything, show the owner your plan (what you will build, which files, which checks, what is left for later) and wait for the owner's "go" (asked with a pop-up question).
3. Work only in your core's files and the files your brief allows. A change another core owns goes on `docs/cores/BOARD.md` (what, why, which file).
4. **The map is being rebuilt (Round T, Release core):** do not change world positions or these files: `js/world.js`, `js/roads.js`, `js/regions.js`, `js/cities.js`, `js/town.js`, `js/homes.js`, `js/vendors.js`, `js/hawkers.js`, `js/places.js`, `js/solids.js`, `js/content/map.js`. Use places and characters by their id only.
5. Do not bump the version (`sw.js` VERSION, `js/build.js`, `studio/version.json`), do not merge into `main`, do not deploy. Commit locally as you go.
6. **Push your own branch without asking once your checks pass** (owner, 10 Oct), and only to this chat's own branch (the one the session was given, or `core/<name>`), never to `main`. Run `git pull --no-rebase` first. If a pull request is opened, keep it a draft: only Release merges.
7. No emoji in docs. **Everything a child sees is drawn with our own art (owner, 24 Oct AEDT):** every picture and emoji in the game is our drawing in `js/art.ts`, never a phone emoji, on screen and on canvases; a new picture gets a new drawing of its own, not another one borrowed. Touch targets 44 px or more (64 px for under-5s). English and Vietnamese for everything a child sees or hears. Times in AEST.
8. Never weaken, skip or delete a check to make it pass: fix the code. If a check is wrong, explain why before changing it.
9. New spoken lines: if `AZURE_SPEECH_KEY` is set, record them with `node tools/make-voice-pack.mts --engine azure` (never print or commit the key); otherwise list them in the report. Lines with a child's name are never recorded (HANDOFF rule 11).
10. Before reporting, run your core's checks, the checks your brief names and any new ones, then `cd tests && node suite.mjs --changed` (the checks for what you changed; see "Checks and the full suite" above). Release runs the full suite (`node suite.mjs`) once per release. Online checks may say "skipped" in a helper chat: say so. **Record the result in your core file's progress notes** (commit id, every check with pass, fail or skipped, date AEST): Release reuses it instead of running the suite again when it merges only your branch (owner, 10 Oct).
11. **The report** lists: what changed (files), every check with pass, fail or skipped, the screenshots you looked at (phone, tablet, computer), new spoken lines (recorded or not), anything not done, decisions the owner made (also written into your core file under "Owner's decisions"), your branch name and last commit id.

Everything else about the project (requirements, how it's built, testing, working style) is in `HANDOFF.md`. Read it first.
